💡About

Off-Grid is a peer-to-peer, end-to-end encrypted messaging system that operates entirely without the internet. Designed for campus environments, it lets two users communicate securely over local Wi-Fi sockets, Bluetooth, or ESP-NOW radio — with all cryptography and storage handled by a pure Java application running on any standard JVM.

Why Off-Grid? In disaster scenarios, censorship-heavy environments, or simply in campus dead-zones, internet-dependent messengers fail. Off-Grid keeps you connected when everything else goes dark.

✨Key Features

🔐

True E2EE

AES-256-GCM encryption via Java Cryptography Architecture (JCA). Messages are stored as ciphertext — even a stolen database is useless without the key.

📴

Zero Internet

Communicates over direct Wi-Fi sockets, Bluetooth RFCOMM, or ESP-NOW radio. No routers, no servers, no cloud.

🗄️

Local SQLite Storage

Chat history persists in an embedded chat_store.db file with WAL journaling for safe, fast writes.

🖥️

Swing GUI + CLI

A clean Swing desktop frontend plus a lightweight CLI demo — choose whichever interface fits your workflow.

📦

Single Fat JAR

Maven Shade plugin bundles everything into one portable chat-app.jar. Just java -jar and go.

⚡

Multi-threaded

Reader, Writer, and UI threads run concurrently via ExecutorService — no lag, no blocking.

🚀Quick Start

Prerequisites

  • Java 17+ (JDK) — Download Adoptium Temurin
  • Maven 3.8+ (optional — you can compile manually with javac)

Option A — Compile manually (no Maven)

# Compile all sources
javac -cp sqlite-jdbc-3.46.1.3.jar -d build ChatDatabase.java ChatFrontend.java ChatDemo.java

# Run the Swing GUI
java -cp "build;sqlite-jdbc-3.46.1.3.jar" chat.ChatFrontend        # Windows
java -cp "build:sqlite-jdbc-3.46.1.3.jar" chat.ChatFrontend        # macOS / Linux

# Or run the CLI demo
java -cp "build;sqlite-jdbc-3.46.1.3.jar" chat.ChatDemo             # Windows
java -cp "build:sqlite-jdbc-3.46.1.3.jar" chat.ChatDemo             # macOS / Linux

Option B — Maven build

# Build fat JAR
mvn clean package

# Run
java -jar target/chat-app.jar

🔄Data Flow

Outbound (Sending)

  1. User types message in the GUI / CLI
  2. Java encrypts payload with AES-256-GCM (JCA)
  3. Ciphertext is framed & chunked into byte segments (< 247 bytes)
  4. Chunks stream to peer via Wi-Fi socket / Bluetooth / Serial → ESP-NOW

Inbound (Receiving)

  1. Encrypted frame arrives from peer transport
  2. Java parses frame headers, reassembles chunks
  3. Payload decrypted, 128-bit auth tag verified
  4. Plaintext written to local SQLite DB and displayed in chat

🛡️Security Model

Encryption

  • AES/GCM/NoPadding — 256-bit key
  • 128-bit authentication tag per message
  • Standard javax.crypto.Cipher (JCA)

Key Management

  • javax.crypto.KeyGenerator for AES-256
  • Java KeyStore (PKCS12) for persistent storage
  • Keys never leave the local machine
⚠️ Current Phase Note: The current codebase uses Base64-encoded plaintext as a placeholder for ciphertext. This is intentional — the real AES-256-GCM layer will replace this in Phase 4, Task 4.3. Do not deploy the current demo as a secure messenger.

🗃️Database Schema

CREATE TABLE IF NOT EXISTS messages (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    sender_id        TEXT    NOT NULL,
    direction        TEXT    NOT NULL CHECK (direction IN ('IN','OUT')),
    timestamp_epoch  INTEGER NOT NULL,
    ciphertext_b64   TEXT    NOT NULL,     -- AES-GCM ciphertext (Base64)
    nonce_b64        TEXT    NOT NULL,     -- GCM nonce / IV (Base64)
    plaintext_cache  TEXT                  -- optional convenience cache
);

CREATE INDEX IF NOT EXISTS idx_messages_ts ON messages(timestamp_epoch);

Ciphertext is stored at rest — a stolen chat_store.db alone does not expose message content.
